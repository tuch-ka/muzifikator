# Design

## Context

См. `proposal.md` — Why. Есть `speech/` с провайдером edge-tts, файловым кэшем и
`AudioTools` (ffmpeg/ffprobe, рык). Хранилище и preflight готовы; `models/` уже в
`.gitignore`. Машина — Apple M4 Pro, `torch` и `transformers` ещё не установлены.
Владелец выбрал `musicgen-small`, без кэша музыки, сегменты с кроссфейдом 2 с,
случайный seed с сохранением в результате.

## Goals / Non-Goals

**Goals:**

- Трек нужной длины, не зависящий от окна модели в 30 с.
- Воспроизводимость: тот же seed и промпт дают тот же файл, seed возвращается.
- Быстрая проверка без скачивания весов: генератор модели отделён от сборки.

**Non-Goals:**

- Кэш музыки и его лимит (решение владельца: без кэша).
- Микс, дакинг, фейды, обрезка до точной длительности речи (фаза 5).
- Мелодическое кондиционирование, продолжение аудио как промпта, fine-tuning.
- Выбор модели и seed из UI; прогресс генерации (фаза 6).

## Decisions

### 1. Зависимости и раскладка

Runtime: `torch`, `transformers`. Numpy приходит с ними; `scipy` не добавляем —
WAV пишется через stdlib `wave` и numpy.

```
src/muzifikator/media.py           # MediaTools: run, probe_duration, concat, crossfade_concat
src/muzifikator/music/base.py      # MusicRequest, MusicResult, протоколы, ошибки
src/muzifikator/music/backend.py   # MusicBackend (protocol) + TransformersBackend
src/muzifikator/music/musicgen.py  # MusicGenProvider: сегмент → WAV через backend
src/muzifikator/music/service.py   # plan_segments, seed, сборка, замер
```

`speech/audio.py` перестаёт владеть ffmpeg-обвязкой: `AudioTools` становится
подклассом `MediaTools` и добавляет только рык. Поведение речи не меняется —
тесты фазы 3 должны пройти без правок логики.

Альтернатива: свой `_run` в музыке — дублирование обработки ошибок ffmpeg.

### 2. Разделение «провайдер музыки» и «бэкенд модели»

`MusicBackend` — синхронный протокол: `load()` (идемпотентно), `generate(prompt,
seconds, seed) -> numpy.ndarray`. `TransformersBackend` держит модель и
процессор, грузит их лениво и один раз.

`MusicGenProvider` реализует `MusicProvider`: принимает `prompt`, `seconds`,
`seed`, `target` и пишет WAV через numpy + `wave`.

Зачем: юнит-тесты сервиса и провайдера идут на фейковом бэкенде без скачивания
2 ГБ весов; реальная модель проверяется отдельным маркером.

Альтернатива: тестировать только настоящую модель — минуты на прогон и сеть в
каждом тесте.

### 3. Параметры генерации

- `MUSICGEN_MODEL` — по умолчанию `facebook/musicgen-small`.
- `MUSIC_MODELS_DIR` — по умолчанию `models/`, передаётся как `cache_dir` в
  `from_pretrained`, поэтому веса не уезжают в домашний кэш HF.
- `MUSIC_PROMPT` — по умолчанию `folk metal`.
- `MUSIC_DEVICE` — `auto` (по умолчанию), `mps`, `cpu`. `auto` выбирает `mps`,
  если доступно. На MPS считается в `float32` (как записано в архитектуре).
- `do_sample=True`, `guidance_scale=3.0`,
  `max_new_tokens = (seconds + 0.25) * 50` (MusicGen отдаёт 50 токенов в секунду
  при 32 кГц). Запас 0,25 с — измеренная поправка: модель отдаёт примерно на
  0,06 с меньше запрошенного при любом размере сегмента, без запаса результат
  оказывался короче запрошенного.

### 4. Seed

`seed = request.seed if not None else secrets.randbelow(2**32)`. Для сегмента `i`
используется `torch.manual_seed(seed + i)`, поэтому базовый seed полностью
определяет трек. Формула выводимая и документируется; `seed + i` без переполнения
проверяется тестом на большом seed.

Воспроизводимость гарантируется в пределах одного окружения (та же модель, версия
`torch`, устройство): на разных устройствах и версиях библиотеки результаты могут
отличаться — это записано в спеку и док.

### 5. План сегментов

Окно модели `window = 30` с, кроссфейд `xfade = 2` с. Алгоритм:

```
lengths = []
assembled = 0
while assembled < duration:
    remaining = duration - assembled
    length = min(window, remaining + (xfade if lengths else 0))
    lengths.append(length)
    assembled = sum(lengths) - xfade * (len(lengths) - 1)
```

Результат: 30 → `[30]`, 40 → `[30, 12]`, 55 → `[30, 27]`, 90 → `[30, 30, 34→30, ...]`
и суммарная длительность всегда не меньше запрошенной, без больших перекосов при
чуть большей длительности.

Альтернатива: генерировать все сегменты по 30 с — для 31 секунды сгенерировали бы
58 секунд музыки, то есть вдвое больше нужного.

Минимальная длина сегмента — 1 с; при меньшей потребности сегмент добирается до
1 с (длительность всё равно не меньше запрошенной).

### 6. Сборка кроссфейдом

`crossfade_concat` строит `filter_complex` из последовательных `acrossfade`:
`[0][1]acrossfade=d=2:c1=tri:c2=tri[a1];[a1][2]acrossfade=...`, выход —
`pcm_s16le` WAV. Один сегмент переносится без перекодирования.

Альтернатива: `concat` встык — щелчки и разрыв ритма на стыках, владелец выбрал
кроссфейд.

### 7. Сервис

`MusicService(provider, ffmpeg_bin, ffprobe_bin, default_prompt, crossfade_seconds=2.0)`.
`generate(request, workdir) -> MusicResult`:
1. Проверить длительность (`>= 1 с`) — до загрузки модели.
2. Промпт: из запроса, иначе `default_prompt`.
3. Seed: из запроса, иначе случайный.
4. План сегментов, генерация каждого в `workdir`.
5. Сборка (один сегмент — как есть, иначе кроссфейд).
6. Длительность через `ffprobe`; если меньше запрошенной — ошибка.
7. Возврат пути, длительности, seed, промпта, модели и числа сегментов.

`workdir` — обязательный параметр: слой музыки не решает, где хранить результат
(фаза 5/6 задаст рабочий каталог). Временные сегменты удаляются в `finally`.

Кэша нет по решению владельца: второй такой же запрос снова генерацию выполняет.

### 8. Ошибки

`MusicError` — база; `MusicModelError` (загрузка весов), `MusicGenerationError`
(сбой генерации), `MusicResourceError` (нехватка памяти, отказ устройства,
сеть при первом скачивании). Все сообщения на русском с моделью и причиной.
Частичный WAV удаляется: результат пишется в `*.part.wav` и переименовывается
только после успешной записи.

### 9. Проверка

- Юнит-тесты `plan_segments`: границы 30/40/55, минимальный сегмент, суммарная
  длительность.
- `crossfade_concat` на реальном ffmpeg: 3+3 с с кроссфейдом 1 с даёт ≈5 с.
- Провайдер с фейковым бэкендом: seed доходит (`seed + i`), бэкенд грузится один
  раз на две генерации, WAV валиден по `ffprobe`.
- Сервис с фейковым провайдером (пишет тишину через ffmpeg): число сегментов,
  длительность ≥ запрошенной, seed возвращается, ошибка при длительности < 1,
  ошибка бэкенда не оставляет файла.
- Реальная модель — маркер `model`, по умолчанию не запускается; ручной прогон в
  задачах фиксирует время генерации 10 с на MPS.

## Risks / Trade-offs

- Первый запуск скачивает ~2 ГБ весов и грузит модель десятки секунд → ошибка с
  понятным сообщением и запись в `docs/operations.md`; модель в памяти до конца
  процесса.
- Генерация на MPS с `float32` заметно медленнее реального времени → прогресс
  появится в фазе 6, сейчас честно документируем ожидания.
- Независимые сегменты с одним промптом могут давать смену «настроения» на
  стыках; кроссфейд сглаживает, но не устраняет → приемлемо; продолжение по
  аудио-промпту — отдельное улучшение.
- Воспроизводимость между устройствами не гарантируется → спека ограничивает
  обещание одним окружением.
- Отсутствие кэша делает повторные генерации дорогими → осознанное решение:
  каждый трек уникален, seed даёт повтор при необходимости.
- WAV на 32 кГц моно ≈ 3,8 МБ в минуту во временном каталоге → удаляется
  вызывающей стороной после микса (фаза 5/6).
- `torch`/`transformers` тяжелы для окружения (~1 ГБ wheels) → отдельного extra
  не делаем, как решено в roadmap («CUDA-сборка документируется одной строкой»).

## Migration Plan

Схема БД не меняется. Появление: `uv sync` (torch и transformers — долгая
установка), первый запуск скачивает веса в `models/`. Откат — revert коммита,
`models/` удаляется вручную. Настройки новые, но с дефолтами: старые `.env`
остаются рабочими.

## Open Questions

Нет: устройство (`auto`), окно (30 с) и кроссфейд (2 с) фиксированы; при
необходимости меняются константами без изменения контракта.
