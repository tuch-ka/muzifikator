# Design

## Context

См. `proposal.md` — Why. `AssemblyService.render` сейчас считает
`needed = речь + хвост`, `Mixer.mix` проверяет длину музыки и обрезает выход по
этому же значению; `jobs/pipeline.py` запрашивает у музыки
`речь + хвост + 0.3`. `MUSIC_PROMPT`-подобные настройки живут в `Settings`.
Владелец выбрал 20 секунд по умолчанию и только конфигурацию.

## Goals / Non-Goals

**Goals:**

- Короткая фраза даёт полноценный трек, в котором музыка разворачивается.
- Одно правило длительности для сборки и запроса музыки.
- Никаких изменений в UI и схеме БД.

**Non-Goals:**

- Настройка минимума из интерфейса и хранение в `settings`.
- Отдельный тип «интро/аутро» и структурная генерация.
- Изменение модели музыки.

## Decisions

### 1. Настройка

`Settings.music_min_duration_seconds: float` (`MUSIC_MIN_DURATION_SECONDS`,
по умолчанию `20.0`, валидация `> 0`). Минимум не хранится в таблице `settings`:
это инженерный параметр окружения, как `MUSIC_PROMPT`, а не пользовательский
выбор; менять — перезапуском.

### 2. Целевая длительность — в сборке

`AssemblyService` получает `min_duration_seconds` в конструкторе.
`render` считает:

```
target = max(speech_duration + tail_seconds, min_duration_seconds)
```

и передаёт `target` в `Mixer.mix`. Сборка проверяет музыку против `target`,
обрезает выход по `target` и позиционирует `afade` по фактической длине музыки.

Почему не в миксере: правило длительности — часть контракта результата и
настройка приложения; миксер остаётся про громкость и переходы.

### 3. Запрос музыки

Пайплайн считает ту же формулу через `deps.assembly.min_duration_seconds` и
просит `target + 0.3` — запас на фейд-аут и округление энкодера. Формула живёт в
двух местах только потому, что это разные процессы; обе используют одну
настройку, расхождение ловится тестом «музыка не короче сборки» на уровне API.

Альтернатива — метод `AssemblyService.required_music_duration(speech)` и вызов
из пайплайна: предпочтительнее, и так и делается — пайплайн не дублирует
арифметику.

### 4. Влияние на смежные части

- Хвост 2 с не меняется: после речи всегда минимум 2 с музыки, при короткой речи
  — больше.
- Фейд-аут остаётся 2 с в конце файла: при длинном хвосте музыка успевает
  вернуться к полному уровню после речи и плавно уйти в конце.
- Записи истории и листинг не меняются.

### 5. Проверка

- Конфигурация: дефолт 20, `0` и отрицательное отвергаются.
- Сборка: речь 1 с, минимум 5 → файл ≈ 5 с; речь 6 с, минимум 5 → ≈ 8 с
  (речь + хвост); музыка короче `target` → ошибка.
- Пайплайн/API: с минимумом 5 короткий текст даёт ≈ 5 с и музыку,
  запрошенную на 5+. Проверяется через фейковый провайдер (он пишет ровно
  запрошенное), поэтому расхождение формул сразу упадёт.
- Существующие тесты с минимумом по умолчанию: сборка в тестах создаётся с
  явным маленьким минимумом, чтобы не генерировать 20 с на каждый кейс.

## Risks / Trade-offs

- Каждая короткая фраза теперь занимает минимум 20 с генерации музыки → на MPS
  это десятки секунд на задачу; осознанная плата за полноценный трек.
- Файлы становятся длиннее → больше места в `OUTPUT_DIR`.
- Минимум — глобальный для всех задач → нельзя попросить короткий трек без смены
  настройки; при необходимости появится параметр в постановке.
- Правило `max(...)` дублируется в сборке и пайплайне в виде вызова одного
  метода → регрессия возможна только при обходе метода, что видно в тестах.

## Migration Plan

Схема и данные не меняются. Старые файлы короче 20 с остаются как есть. Откат —
revert коммита и убрать переменную; поведение вернётся к «речь + 2 с».

## Open Questions

Нет: значение по умолчанию, место настройки и отношение к итоговому файлу
зафиксированы владельцем.
