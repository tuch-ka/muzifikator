# Design

## Context

См. `proposal.md` — Why. Готовы: `SpeechService.synthesize` (MP3 + длительность),
`MusicService.generate(request, workdir)` (WAV, длительность ≥ запрошенной),
`AssemblyService.render` (MP3+M4A в `OUTPUT_DIR`), хранилище с `generations` и
синхронными сессиями, preflight, FastAPI-приложение с `create_app(preflight)`.
Все сервисы синхронные и тяжёлые (сеть, torch, ffmpeg). Схема `generations` уже
содержит статус, стадию, ошибку, длительность и `output_path`.

## Goals / Non-Goals

**Goals:**

- Запрос постановки возвращается сразу, работа идёт в фоне, состояние читается
  опросом.
- Ни один шаг не оставляет историю в состоянии «вечно running».
- Сервисы остаются как есть: оркестратор их только вызывает.

**Non-Goals:**

- Отмена, приоритеты, несколько воркеров, очередь ожидания.
- Прогресс в процентах: стадия — достаточная гранулярность.
- Работа в отдельных процессах или через брокер: один процесс, один воркер-поток.

## Decisions

### 1. Менеджер задач и один рабочий поток

`JobManager` хранит `threading.Lock`, признак занятости и идентификатор текущей
задачи. `submit(generation_id, work)` под локом проверяет занятость: занято —
возвращает текущий id (роут отвечает `409`), свободно — помечает занятость и
запускает `threading.Thread(daemon=True)`.

`daemon=True` осознанно: при остановке процесса воркер не должен удерживать
завершение на минуты генерации; задача останется `running`, и её снимет
восстановление при следующем старте.

Альтернативы: `BackgroundTasks` FastAPI — выполняется после ответа в том же пуле
потоков и не даёт контроля над занятостью; `ProcessPoolExecutor` — отдельный
процесс, дублирует загрузку модели и базы.

### 2. Пайплайн и стадии

`run_generation(generation_id, request, deps)` — обычная функция, вызываемая в
потоке. Каждая стадия: обновить стадию и закоммитить, затем сделать работу.

1. `start_generation` (pending → running), стадия `tts`, синтез речи.
2. `set_stage(music)`: музыка длиной `речь + хвост + 0.3 с` во временном каталоге
   внутри `OUTPUT_DIR`.
3. `set_stage(mix)`: сборка; файлы записываются в базу.
4. `finish_generation`: `output_path` — путь MP3 (совместимость со спекой
   истории), длительность из результата сборки.

Ошибка на любой стадии: `fail_generation` с текстом, временные файлы удаляются,
связей с файлами нет.

Почему стадия пишется до работы: опрос во время долгой стадии должен показывать
именно её, а не предыдущую.

### 3. Сессия на поток

Каждый воркер открывает свою сессию из фабрики и закрывает её в `finally`.
SQLite настроен на `check_same_thread=False` и WAL, поэтому сессия из другого
потока безопасна, но переиспользовать одну сессию между потоками нельзя.

### 4. Таблица файлов результата

Новая миграция:

```sql
CREATE TABLE generation_files (
    generation_id VARCHAR(32) NOT NULL REFERENCES generations(id) ON DELETE CASCADE,
    format VARCHAR(8) NOT NULL,
    path TEXT NOT NULL,
    PRIMARY KEY (generation_id, format)
);
```

Составной ключ `(generation_id, format)` не даёт двум строкам одного формата
существовать; отдельный `id` не нужен. `ON DELETE CASCADE` — на случай будущей
чистки истории. Репозиторий: `add_generation_file`, `list_generation_files`,
`get_generation_files(generation_id) -> dict[format, path]`.

Альтернатива JSON-колонка — отклонена владельцем: поиск по формату и целостность
дороже, чем одна миграция.

### 5. API

| Метод | Путь | Коды |
|---|---|---|
| `POST` | `/api/generations` | `202` с id и статусом; `400` неизвестный голос/формат; `409` занято; `422` пустой текст |
| `GET` | `/api/generations/{id}` | `200` состояние; `404` нет задачи |
| `GET` | `/api/generations` | `200` список новых первыми, `limit` 1..100 (20 по умолчанию) |
| `GET` | `/api/voices` | `200` голоса; `502` провайдер недоступен |

Тело постановки: `text`, `voice`, необязательные `tts_provider`, `rate_percent`,
`pitch_hz`, `growl`, `music_tags`, `music_seed`, `formats`. Валидация форматов и
текста — до создания записи.

Проверка голоса требует списка провайдера: первый POST в процессе платит за
сетевой запрос, дальше список кэширован в провайдере. Если список получить
нельзя, постановка отвечает `502`, а не создаёт заведомо падающую задачу.

### 6. Зависимости приложения

`create_app(preflight, *, engine, session_factory, jobs=None)` — `jobs` это
`JobManager` с уже собранными сервисами и фабрикой сессий. Если `jobs` нет,
эндпоинты отвечают `503`: приложение остаётся запускаемым для health и тестов
слоёв.

Сборка сервисов — в `__main__.py`: один провайдер edge-tts (он же кэширует
голоса), один `SpeechService`, один `MusicService` с `TransformersBackend`
(модель грузится лениво при первой задаче), один `AssemblyService`.

### 7. Восстановление после рестарта

`fail_stale_generations(session, reason)` меняет все `running` на `failed` с
`finished_at` и текстом «прервано перезапуском». Вызывается в lifespan
приложения при старте: это гарантирует и обычный запуск, и тесты. Ошибка сброса
не должна мешать старту — логируется.

### 8. Ошибки API

- `UnknownVoiceError` → `400`, текст содержит голос.
- `UnknownFormatError` → `400` до создания записи.
- `VoiceListError` на постановке → `502`.
- Занято → `409` с `generation_id` текущей задачи.
- Pipeline-ошибки не всплывают в HTTP: они остаются в записи и видны опросом.

### 9. Проверка

Тесты на `TestClient` с фейковыми провайдерами (пишут тон нужной длины) и
настоящим `AssemblyService` на ffmpeg:

- постановка → опрос до `done`, два файла в ответе и в `generation_files`;
- занятость: провайдер блокируется `threading.Event`, второй POST → `409` с id,
  после разблокировки первый доходит до `done`;
- ошибка провайдера → `failed` с текстом и без файлов;
- восстановление: строка `running` в базе → `failed` после старта приложения;
- `GET /api/voices` и `502` при ошибке провайдера;
- `404`, `422`, `400` для неизвестных id, пустого текста и плохого формата;
- миграция добавляет таблицу, `alembic upgrade head` идемпотентен.

## Risks / Trade-offs

- `daemon`-поток убивается при остановке: задача остаётся `running` до
  следующего старта → состояние выправляется восстановлением, но не мгновенно.
- Single-flight только внутри процесса: второй экземпляр приложения на той же
  базе его обойдёт → один процесс на базу уже зафиксирован в `storage-schema`.
- Проверка голоса на POST добавляет сетевой вызов в первый запрос → список
  кэшируется провайдером на процесс.
- Долгая генерация держит поток: остановка сервера не ждёт её (daemon), но и не
  отменяет — временные файлы остаются до следующей уборки.
- Поток с torch: модель грузится в рабочем потоке, MPS работает; при смене
  устройства поведение не проверялось на CUDA.
- `output_path` дублирует путь MP3 из `generation_files` → дублирование
  осознанно, чтобы существующая спека истории не менялась.

## Migration Plan

`alembic upgrade head` при старте добавит `generation_files`. Существующие
записи остаются без файлов — это корректно: до фазы 6 файлов не было. Откат —
revert коммита и `alembic downgrade -1`; данные истории при откате не теряются.
