# Design

## Context

См. `proposal.md` — Why. В репозитории 134 теста, маркеры `network` и `model`
исключены по умолчанию (`addopts` в `pyproject.toml`). `music/backend.py`
импортирует `torch` и `transformers` на уровне модуля, поэтому тест-прогон
требует их установки даже без модельных тестов. Тесты используют `ffmpeg` и
`ffprobe`. OpenSpec CLI ставится из npm (`@fission-ai/openspec@2.1.1`). Процесс
(`AGENTS.md`): ветка и PR появляются на гейте архива, merge — только владельцем.

## Goals / Non-Goals

**Goals:**

- Красный PR на любое нарушение линта, тестов или спек — без ручных команд.
- Прогон укладывается в разумные минуты: CPU-вариант `torch`, кэш `uv`.
- Возможность проверить сам workflow до открытия PR.

**Non-Goals:**

- Проверка модельных и сетевых тестов в CI: они требуют весов/сети и минуты
  времени, для PR это не нужно.
- Кэширование `models/` между прогонами.
- Матрица Python/OS, публикация пакета, релизные артефакты.

## Decisions

### 1. Один job на ubuntu-latest

Один job `checks` с шагами: checkout → `setup-uv` с кэшем → `uv sync --locked` →
установка `ffmpeg` → линт → тесты → `openspec validate` → `uv build` и проверка
установки wheel. `timeout-minutes: 20`, `concurrency` с `cancel-in-progress`.

Почему не матрица и не отдельные jobs: прогон короткий, а разделение на jobs
добавляет повторную установку зависимостей и время на старт раннеров.

### 2. CI не устанавливает torch

Основной job ставит зависимости так:

```
uv sync --locked --no-install-package torch --no-install-package transformers
```

Тестам torch не нужен: модельные тесты отключены маркером, а единичные тесты
музыки работают на фейковых бэкендах. Для этого:

- `music/backend.py` импортирует `torch` и `transformers` внутри `load()` и
  `generate()`, а типы берёт под `TYPE_CHECKING`; импорт `muzifikator.music`
  больше не тянет torch;
- `numpy` добавляется явной зависимостью: код использует его напрямую, сейчас он
  приходит только через `transformers`.

Выигрыш: ~60–90 с прогон с тёплым кэшем вместо 2–3 минут, и холодный прогон не
скачивает ~1 ГБ. Локальная установка (`uv sync`) не меняется — torch остаётся
зависимостью.

Проверкой служит сам лёгкий прогон: пакет `music` импортируется и тесты идут в
окружении без torch, значит ленивые импорты корректны. Обратная сторона —
сборка wheel проверяется без зависимостей, поэтому ошибку импорта внутри
`load()` CI не увидит; её ловит модельный тест локально.

Альтернативы: свой образ в GHCR с предустановленным torch — pull 2–3 ГБ и conda
python внутри, `uv` всё равно ставит зависимости проекта заново, плюс
сопровождение образа; Docker Hub-образы `pytorch/pytorch` по той же причине не
дают выигрыша.

### 3. mypy: строгий режим только для `src`

```toml
[tool.mypy]
files = ["src"]
strict = true
python_version = "3.12"
warn_unused_ignores = true

[[tool.mypy.overrides]]
module = ["torch", "torch.*", "transformers", "transformers.*"]
ignore_missing_imports = true
```

Почему только `src`: тесты проверяют поведение, аннотировать 134 теста ради
mypy — бумажная работа без отдачи. Почему `strict`: код небольшой, и все новые
модули фаз 6–11 сразу попадут под строгий режим; ослабить всегда можно, ужесточать
задним числом — дороже.

Почему `ignore_missing_imports` для `torch`/`transformers`: в лёгком CI этих
пакетов нет, а mypy должен видеть хоть какие-то стабы. Цена — тела вызовов модели
типизируются как `Any`; всё, что вокруг (наши dataclass'ы, протоколы, работа с
файлами), проверяется строго. Граница `Any` зафиксирована в `backend.py`, выше не
протекает.

mypy ставится dev-зависимостью и запускается в CI между линтом и тестами:
ошибка типа дешевле падения теста по времени разбора.

Альтернативы: отдельная фаза типизации после CI — второй проход по уже
написанному коду; `strict` для тестов — много правок без выигрыша; ставить
`torch` в CI ради стабов — +1 ГБ на каждый прогон.

### 4. CPU-индекс `torch` только для Linux

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = [{ index = "pytorch-cpu", marker = "sys_platform == 'linux'" }]
```

`explicit = true` не подменяет индекс для остальных пакетов. На macOS маркер не
срабатывает, локальная установка не меняется. Альтернатива — ставить как есть:
на Linux `torch` с PyPI тянет CUDA-зависимости на несколько гигабайт, и прогон
растёт в разы.

Риск: CPU-индекс может не содержать нужную версию `torch` → `uv lock` это
поймает локально, а CI — первым прогоном.

### 5. Кэш зависимостей и lockfile

`astral-sh/setup-uv` с `enable-cache: true`; установка — `uv sync --locked`,
чтобы CI падал при расхождении `uv.lock` и `pyproject.toml`, а не молча
пересобирал lockfile.

Версия Python берётся из `.python-version` (3.12), которую `uv` читает сам.

### 6. Установка ffmpeg

`sudo apt-get update && sudo apt-get install -y ffmpeg` — в ubuntu-latest
`ffmpeg` не предустановлен. Проверка `ffmpeg -version` и `ffprobe -version`
сразу после установки: если apt поменяет состав пакета, падение будет явным.

### 7. OpenSpec в CI

`actions/setup-node` с Node 22 (OpenSpec требует `>= 22.20`), затем
`npm install -g @fission-ai/openspec@2.1.1` — версия совпадает с локальной.
Проверка спек:

```
openspec validate --specs
```

**Дельты активных change в CI не проверяются.** Схема `taxmonitor` подключена
симлинком в `~/zakharov-llm` (`CONSTITUTION.md` п. 6.1) и не копируется в
репозиторий, поэтому на раннере `openspec validate <change>` падает с
`unknown schema 'taxmonitor'`. Первый прогон CI это подтвердил. Дельты
валидируются локально и на `openspec archive`; если понадобится проверять их в
CI, нужно решение владельца о том, как доставлять схему в раннер (вендоринг
схемы меняет конституцию).

Альтернатива: не проверять спеки в CI вовсе — тогда даже основные спеки
остаются без автоматической проверки.

### 8. Сборка и установка wheel

`uv build` → `uv venv .wheelcheck` → `uv pip install --python .wheelcheck/bin/python
--no-deps dist/*.whl` → `.wheelcheck/bin/python -c "import muzifikator"`.
`--no-deps` важен: без него uv потянул бы `torch` и свёл на нет лёгкий CI;
зависимости к этому шагу уже проверены `uv sync --locked`.

sdist ограничен содержимым пакета (`[tool.hatch.build.targets.sdist]`): иначе в
него попадает `openspec/schemas/taxmonitor` — симлинк с абсолютным путём в
`~/zakharov-llm`, и hatchling отказывается собирать архив («unsafe symbolic-link
target»). Первый прогон CI это и показал.

Почему отдельное окружение: проверяется, что пакет ставится и импортируется сам
по себе, без исходников и без лишних зависимостей. Полный импорт `muzifikator`
зависимостей не требует — `__init__.py` пустой по импортам. В CI torch не
установлен, так что этот шаг заодно подтверждает, что сборка не тащит лишнего.

### 9. Триггеры и ручной запуск

```yaml
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:
```

`workflow_dispatch` — для ручных прогонов после merge. Проверить сам workflow до
архива через него нельзя: GitHub требует наличия файла на default-ветке. Поэтому
для этой фазы допускается открыть **draft PR** сразу после коммита кода — событие
`pull_request` запускает workflow из ветки PR. Дальше PR живёт до архива: архивный
коммит его обновляет, на гейте он переводится из draft в ready.

### 10. Настройки репозитория

Обязательность проверки `CI` для merge в `main` (branch protection) —
настройка GitHub, а не файл в репозитории. Владелец включает её вручную;
`docs/ci.md` описывает шаги. Без неё workflow работает, но не блокирует merge.

## Risks / Trade-offs

- Ленивые импорты скрывают ошибку внутри `load()` до первого модельного
  прогона → модельный тест (`-m model`) остаётся обязательным при изменениях
  бэкенда, это записано в `docs/ci.md`.
- `Any` от torch/transformers может скрыть ошибку внутри `backend.py` → граница
  `Any` держится в одном модуле, остальной код типизирован строго; при появлении
  стабов `torch` override снимается.
- `npm`-пакет OpenSpec может измениться → версия закреплена, обновление — вместе
  с локальной версией CLI.
- Раннеры `ubuntu-latest` дрейфуют → apt-пакет `ffmpeg` и версия Node не
  закреплены; падение будет явным на шаге проверки версий.
- Лимит минут GitHub Actions для приватного репозитория → один короткий job на
  PR; модельные тесты в CI не идут.
- CPU-индекс PyTorch CI не использует (torch не ставится) → он нужен только
  полной установке на Linux; его недоступность CI не задевает.
- Проверка wheel без зависимостей не ловит ошибки импорта `music`/`speech` →
  это покрыто тестами, а не сборкой.

## Migration Plan

Файловых данных нет. Порядок: правка `pyproject.toml` → `uv lock` локально →
workflow → проверка `workflow_dispatch` на ветке → PR фазы. Откат — revert
коммита; на настройки репозитория откат не влияет.
