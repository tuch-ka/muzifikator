# Design

## Context

См. `proposal.md` — Why. Есть `create_app` с эндпоинтами health, задач и голосов
(в одном `app.py`), `Settings` на `pydantic-settings`, таблица `settings` с
JSON-значениями и `get_setting`/`set_setting`, `OUTPUT_DIR` с готовыми файлами.
Владелец выбрал один корень, белый список настроек, только листинг, без
эндпоинта корней.

## Goals / Non-Goals

**Goals:**

- UI получает полный список готовых файлов и сохранённые настройки, ничего не
  зная о файловой системе напрямую.
- Невозможно выйти за выходной каталог через API.
- Настройки реально влияют на новые задачи.

**Non-Goals:**

- Скачивание, стриминг, загрузка файлов.
- Несколько корней, выбор корня в UI.
- Кэш листинга и постраничная выдача.
- Авторизация: сервис слушает loopback.

## Decisions

### 1. Пакет `api/` и роутеры вместо одного `app.py`

```
src/muzifikator/api/__init__.py
src/muzifikator/api/files.py        # build_files_router(output_dir)
src/muzifikator/api/settings.py     # build_settings_router(store)
src/muzifikator/api/settings_store.py  # белый список, чтение/запись, ошибки
src/muzifikator/api/generations.py  # build_generations_router(session_factory, jobs)
```

Каждый роутер — функция-фабрика с замыканием на зависимости; `create_app`
собирает их и остаётся тонким. Эндпоинты задач и голосов переезжают из `app.py`
без изменения контрактов — это рефакторинг перед фазой 9, где добавится
статический UI.

Альтернатива: продолжать растить `app.py` — к UI он станет свалкой из
пятнадцати обработчиков.

### 2. Листинг и защита путей

Корень — `OUTPUT_DIR`, приводится к абсолютному `resolve()` при создании
роутера; каталог создаётся, если его нет.

Проверка пути:

1. `path` не содержит `\x00` и не абсолютный — иначе `400`.
2. `(root / path).resolve()` — раскрывает `..` и симлинки.
3. Результат должен быть внутри корня (`is_relative_to`) — иначе `400`; это
   отсекает и `..`, и симлинк наружу одной проверкой.
4. Нет файла — `404`; не каталог — `400`.

Ответ: `{root, path, entries: [{name, path, kind, size, modified_at}]}`, где
`path` записи — относительно корня в posix-виде. Сортировка: каталоги, затем
имя без учёта регистра. Скрытые файлы попадают в список: они часть выхода
(`.tmp-*` при сбое) и их полезно видеть.

Альтернатива: проверять строку на `..` до resolve — не ловит симлинки.

### 3. Белый список настроек

| Ключ | Тип | Умолчание |
|---|---|---|
| `tts_voice` | строка, непустая | нет (`null`) |
| `music_tags` | строка, непустая | `MUSIC_PROMPT` |
| `rate_percent` | int −100..200 | 0 |
| `pitch_hz` | int −100..100 | 0 |
| `growl` | bool | false |
| `output_formats` | список из `mp3`/`m4a`, непустой | `OUTPUT_FORMATS` |

`GET /api/settings` отдаёт действующие значения (сохранённое или умолчание).
`PATCH /api/settings` принимает подмножество: сначала валидируются все ключи,
потом одной транзакцией пишутся в `settings`. Неизвестный ключ или плохое
значение — `400` с именем ключа, ничего не сохраняется.

Ключи плоские (`tts_voice`, `music_rate_percent` не нужно — хватает
`rate_percent`), потому что таблица `settings` и так хранит их отдельными
строками.

### 4. Настройки как умолчания постановки

`GenerationCreate` получает `voice`, `music_tags`, `rate_percent`, `pitch_hz`,
`growl`, `formats` как необязательные (`None` — «не указано»). Роутер читает
настройки и подставляет:

- `voice`: из запроса, иначе из `tts_voice`; если нигде нет — `422`;
- `music_tags`, `rate`, `pitch`, `growl`, `formats`: из запроса, иначе из
  настроек.

Проверка голоса по списку провайдера выполняется уже над разрешённым значением.
В историю (`generations`) пишется разрешённый голос и теги — так запись
воспроизводима хотя бы по сохранённым полям.

Почему не в пайплайне: тогда в историю попадёт `null` вместо фактических
параметров, а ошибка «нет голоса» всплывёт асинхронно, после `202`.

### 5. Хранилище настроек

`SettingsStore(session_factory, defaults)` — один объект на приложение.
`read()` открывает сессию и собирает действующий словарь; `update(payload)`
валидирует, пишет и возвращает новое состояние. Ошибки
`UnknownSettingError`/`InvalidSettingError` превращаются в `400` в роутере.

Умолчания берутся из `Settings` при создании приложения: `MUSIC_PROMPT`,
`OUTPUT_FORMATS`. Смена переменной окружения требует перезапуска, как и раньше.

### 6. Ошибки

| Ситуация | Код |
|---|---|
| Путь вне корня, абсолютный, симлинк наружу, путь к файлу | `400` |
| Каталог не найден | `404` |
| Неизвестный ключ настроек, некорректное значение | `400` |
| Нет голоса ни в запросе, ни в настройках | `422` |

### 7. Проверка

`TestClient` на приложении с временным `OUTPUT_DIR` и фейковыми сервисами:

- листинг: сортировка, вложенный путь, пустой каталог, скрытые файлы;
- защита: `..`, абсолютный путь, симлинк наружу, отсутствующий каталог, путь к
  файлу;
- настройки: умолчания, частичное обновление, неизвестный ключ, плохой формат,
  сохранность после пересоздания приложения;
- умолчания задачи: `PATCH` голоса и тегов → `POST` только с текстом →
  провайдер получил теги, в записи голос; без голоса и без настроек — `422`;
  явные параметры главнее;
- старые тесты задач проходят без изменения контрактов.

## Risks / Trade-offs

- Проверка пути через `resolve()` уязвима к гонке (файл подменят между проверкой
  и листингом) → для локального однопользовательского сервиса приемлемо; путь
  всё равно не выходит за корень в момент проверки.
- Листинг без пагинации: большой каталог отдастся целиком → в `out/` личные
  результаты, объём небольшой; пагинация добавляется при необходимости.
- Настройки действуют только на новые задачи → уже поставленная задача
  использует значения, разрешённые в момент постановки.
- `tts_voice` не валидируется при сохранении (список голосов — сеть) → проверка
  происходит при постановке задачи; в настройках может лежать несуществующий
  голос, пока провайдер не ответит.
- Рефакторинг эндпоинтов задач в роутеры затрагивает рабочий код → контракты
  не меняются, старые тесты API должны пройти без правок (кроме новых умолчаний).

## Migration Plan

Схема БД не меняется: используются существующие `settings`. Новых зависимостей
нет. Откат — revert коммита; сохранённые настройки останутся в базе и не помешают
старой версии.

## Open Questions
